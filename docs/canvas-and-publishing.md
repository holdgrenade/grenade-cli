# Canvas and publishing

Part of `grenade-cli`: its rules and invariants are in the repo's `CLAUDE.md`.

## Canvas (`src/canvas/`)

Read PROTOCOL.md "Canvas" first. A group's design canvas is the HTML boards an agent writes in `.grenade/canvas` of the folder the group's sessions share; the Mac app shows them in its toolbox (grenade-mac CLAUDE.md "Canvas"), and a phone asks the daemon for them with `canvas`, `canvas.subscribe`, `canvas.unsubscribe` and `canvas.board` (`canvas: 1` in the `daemon` object, protocol 1.11.0).

- **Several per group** (protocol 1.16.0, `canvases: 1`; Adam, canvas "Grenade Groups, Canvases and Browsers"): a group's canvases are the real folders `canvas-<n>` in `.grenade/canvas/<group>/`, and the boards directly in `.grenade/canvas` are the canvas `shared`. `canvases` lists them (`listCanvases`), named by the protocol's `canvasNameOf` (the first board's `<title>`). The canvas frames take `group` and `canvas`; the daemon checks the `cwd` as before and that a listed session is in `group` (`isListedGroup`), then serves `<cwd>/.grenade/canvas/<group>/<canvas>`. It still makes no folder: the Mac app makes `canvas-<n>` and moves one to another group; a moved link follows with `publish.canvas` `token` (`Publisher.repoint`).

- **Read only, and only there.** `CanvasService.folderOf` serves a `cwd` only when, normalized, it is a listed session's `cwd` or the folder a group of several shares (`canvasAccess.ts`); anything else is `bad_frame` before the disk is touched. The daemon never makes the folder or writes in it. A board is a bare `.html`/`.htm` name (the protocol's `CanvasFileName` refuses a path, a hidden name, NUL) that is a regular file directly in the folder: links are left out of the list and refused when asked for (`O_NOFOLLOW`), and so are a `.grenade` or a `canvas` that is a link. `SECURITY.md` "The design canvas" says what that means for a phone.
- **Too large.** A board over 2 MiB is refused before it is read; one whose `canvas.board` frame would be over 3,000,000 bytes of JSON (a board full of quotes, which JSON doubles) is refused once built (`Connection.handleCanvas`), so a frame sealed for a relay stays under its 4 MiB cap. Both are `bad_frame` with `boardTooLarge`'s sentence.
- **Watching is a poll** (`CanvasWatcher`, 400 ms like the Mac app), not `fs.watch`: the folder may not exist yet, a save may replace the file, and FSEvents and inotify say those things differently. Each look is a `readdir` and an `lstat` per board; a board's head (for its size) is read again only when its save time or size changed. A `canvas.subscribe` replies with the canvas at once (with its `id`), then a `canvas` without `id` whenever `listingKey` changes for that subscriber. A connection keeps its watches by `cwd`, `group` and `canvas` as sent (`watchKey`), at most 8; `canvas.unsubscribe` and the connection closing stop them, and the daemon's `stop` stops every poll. A watch outlives the session that let it in (it was allowed when it began).

## Publishing (`src/publish/`)

Read PROTOCOL.md "Publishing" and "Share host" first. A group's canvas published to a secret link on the share host (`grenade-website/workers/share`, `share.holdgrenade.com`), which anyone with the address opens with no sign-in (`publish: 1` in the `daemon` object, protocol 1.13.0). The Mac app's Publish button asks with `publish.canvas`; the daemon does all the uploading, so a page stays live with the app closed.

- **Only the canvas folders `canvas` serves.** `publishCanvas` asks `CanvasService.folderOf`, so a folder no session works in is `PublishError` (`bad_frame` with the `id`). Once published, a link keeps following its folder after the sessions end.
- **What goes up**: the boards of the scope (read through `readBoard`, so the same 2 MiB cap and no links), and the folder's other files that a published board names by a relative address (`referencedAssets`), never a page and never one none names. The manifest carries each file's SHA-256; the host answers which it lacks, and only those go up. An unchanged canvas sends nothing (the manifest's own SHA-256 is kept as `manifestSha`).
- **Always live, no snapshot** (Mike). Each link watches its folder with the canvas's watcher and uploads 1.5 s after the last change. `newest` moves to a new revision as soon as its first board is saved. A failure is `failed` with the host's sentence and tries again a minute later; an expired link is `expired` and stops.
- **Keys stay here.** published.json (0600) holds each link's key; the host keeps only its SHA-256; no frame, control answer or log line carries a key, and a log names a link by `tokenForLog`. Unpublishing deletes at the host first and forgets the link only once that worked, so a link is never left up and unknown.
- **Who is told**: a connection that sent any publish frame gets `published` on every `changed` (`Connection.watchesPublish`), like `voice`.
- **Not covered by the tests**: the real share host (the Worker's own tests drive it in memory). Checked by hand against `npx wrangler dev` in `workers/share` with `GRENADE_SHARE_URL`: all revisions, then newest, went up and the page and a board alone showed them.

### Comments (`src/publish/comments.ts`, `owner.ts`)

Read PROTOCOL.md "Comments" first (protocol 1.24.0, `comments: 1`). Reviewers comment on a link at the share host, which cannot reach this computer, so `CommentService` pulls each live link's events after its cursor: every 15 s while a connection follows that link (`comments.list` → `watch`), every 2 minutes otherwise, never an expired one. It keeps them in `~/.grenade/comments/<token>.json` (0600) with the cursor and `seen` (per thread, read up to when), so a removed link's comments stay readable. `reply` and `resolve` post the owner's event with the link's key (`ShareClient.postComment`, author `owner` and the owner's name); what the owner answers counts as read. Every change emits `changed` (a `comments` frame), which the connections that follow that link send on, and the publisher's `touch` sends `published` again with each link's `comments {open, unread}` (`commentsOf`). `OwnerName` keeps the owner's name in `~/.grenade/owner.json` (0600), starting as the account's full name (`id -F` on a Mac, none elsewhere); `owner.name` asks or sets it, and a change makes the publisher send every page again with `owner` in its manifest ("Shared by …"). Phones are not pushed about comments (`PushEvent` is a closed list older phones decode). Not covered by the tests: the real share host (checked by hand against `npx wrangler dev`, see grenade-website CLAUDE.md "Share host").
