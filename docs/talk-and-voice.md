# Voice providers and typed Talk

Part of `grenade-cli`: its rules and invariants are in the repo's `CLAUDE.md`.

## Voice providers (`src/voice/`)

Read PROTOCOL.md "Voice providers" first. The owner's API keys for Talk (speech to speech) live on this computer, in `voice-keys.json`, and on no phone. A client asks for a short-lived token (`voice.token`) each time it opens a connection to the provider; the audio never passes through the daemon.

- **A provider is one file and one line.** `VoiceProvider` says its `id`, `name`, `uses` (`talk`, `dictation`) and two pure functions: `tokenRequest(key, ask)` (the POST that makes a token) and `readToken(body, ask)` (the token, when it stops opening connections, and whether it opens one connection only). To add one (a speech-to-text service for the `dictation` use, say), write its file beside `openai.ts`, add it to `VOICE_PROVIDERS`, and add its row to PROTOCOL.md's table. No frame, no schema and nothing in `Connection` changes; the apps need their own code to speak with it. A provider with two uses lists both and tells them apart by `ask.use`.
- **Checking a key is making a token.** `VoiceService.setKey` and `grenade voice key` both call `mintToken` with the provider's first use and no model, and keep the key only when a token came back. It bills nothing. There is no second "is this key good" call to keep in step.
- **What each token is.** OpenAI: a client secret, 60 s to open its one connection; one made for a `model` opens that model only, one made for none opens any (tried against the API). Gemini: `uses: 1`, 60 s to start the session, 30 minutes to speak in it (Talk opens a new session every 8). **Gemini's is written from its docs and has not been tried against the API** (no key at hand): if it fails, look at `tokenRequest`'s body and `readToken`'s field first. Wispr Flow (dictation) was a provider until it closed its API; a daemon drops a key still kept for a provider it no longer has from `voice-keys.json` (`VoiceService.known`).
- **Who is told.** A connection that sent `voice` once gets the `voice` frame on every `changed` (`Connection.watchesVoice`). `voice.key` always answers its sender, once. `grenade voice` writes the file itself and posts `/voice/reload`, so it works with the daemon stopped, and the key never travels over the control API.
- **Never logged, never sent back.** No frame and no control route carries a key, only `maskVoiceKey`'s form. `mintToken` never passes on a failed request's own error text (it can name headers) and takes the key out of a provider's words. `test/voice.test.ts` checks the log, `test/daemon.test.ts` that neither a key nor a token is readable on the socket.

## Typed Talk (`src/talk/`)

Read PROTOCOL.md "Talk by text" and SECURITY.md "Typed Talk" first. The owner types what they want done; for each message the daemon runs Claude Code or Codex headless, with Grenade's tools as its only tools, and the thread of the day gains the rows that follow. No voice key. The daemon says `talk: 1`, and `talk: true` on each agent whose program is found at start (`resolveTalkBin`; not whether it is signed in: a signed-out agent answers with a `failed` row).

- **A turn.** `talk.say` (or `POST /talk/say`) writes the `you` row and queues the words; turns run one at a time, in order, `busy` around them. Each turn gets `newTurn()` (a uuid and a 24-byte secret), and the agent's run gets `GRENADE_TALK_PORT`, `GRENADE_TALK_TURN`, `GRENADE_TALK_SECRET` in its environment. The agent starts `node <cli.js> talk-mcp` (`process.argv[1]`, the script the daemon runs); that server forwards each call to `POST /talk/tool` on the control port, which refuses a call that is not the running turn's (403 "This Talk turn is over."), also after the turn ended. Nothing else starts a turn: no row, no session event.
- **The message.** `--append-system-prompt` / `developer_instructions` carry `TALK_INSTRUCTIONS`; each turn's stdin is `turnMessage`: the sessions in a `<sessions note="…data…">` fence, the project names, the day's rows in short when the conversation is new (first turn of the day, or the agent was switched, or the last turn failed), then "The owner says:" and the words.
- **Claude Code**, in `<GRENADE_HOME>/talk/work`: `claude -p --output-format json --tools "" --strict-mcp-config --mcp-config '{"mcpServers":{"grenade":{"command":"<node>","args":["<cli.js>","talk-mcp"]}}}' --allowedTools mcp__grenade --setting-sources "" --append-system-prompt <rules> --session-id <uuid>` on the conversation's first turn, `--resume <uuid>` after. No built-in tool, no settings (no hooks), no other MCP server; Claude Code passes its own environment to the server. The answer is the JSON's `result`; `is_error` or a non-JSON exit is a failure, worded "not signed in" when it says so.
- **Codex**: `codex exec --json --skip-git-repo-check --ignore-user-config --disable shell_tool --disable unified_exec --disable apps --disable plugins --disable browser_use --disable computer_use --disable in_app_browser --disable image_generation --disable multi_agent --disable goals -c mcp_servers.grenade.command="<node>" -c mcp_servers.grenade.args=["<cli.js>", "talk-mcp"] -c mcp_servers.grenade.env_vars=["GRENADE_TALK_PORT", "GRENADE_TALK_TURN", "GRENADE_TALK_SECRET"] -c mcp_servers.grenade.default_tools_approval_mode="approve" -c developer_instructions="<rules>" -s read-only -C <work> -`, then `codex exec resume <same flags> -c sandbox_mode="read-only" <thread id> -`. Found by running it: exec's approval policy is `never`, so an MCP tool call fails ("requires approval") unless the server's `default_tools_approval_mode` is `approve`; Codex hands a stdio server only the variables `env_vars` names; `--ignore-user-config` keeps the user's other MCP servers and hooks out and still uses `CODEX_HOME`'s login; the `--disable`s take away its shell (it says "shell access isn't available" and still calls Grenade's tools). The thread id is `thread.started`'s, the answer the last `agent_message` of the turn, `turn.failed` / `error` a failure. **Codex 0.160.0 (Homebrew's at the time) cannot call any tool from exec with its default models**: they are `tool_mode: code_mode_only`, and its code-mode host times out ("timed out negotiating with the code-mode host"), so a turn ends after about two minutes with an answer that says it could not reach its tools. Codex 0.160.1 works. `CODEX_BIN` points the daemon at another codex.
- **The rules in code** (`talkTools.ts`, `talkGuard.ts`): `send_to_session` only to a session `route_session` matched for `prompt` in this turn; never to a shell (what it is typed runs), a session that is gone, one waiting for an answer or with an open card, or one whose screen shows a dialog (`agentReady.ts`); one line, 1000 characters, typed with `registry.sendText(id, line, true)`, what a client's `input` does. `create_session` only in a known project named by its folder's name, with a coding agent (`registry.create`, the same as `session.create`), at most 3 a turn; its first prompt waits up to 30 s for the agent's prompt box and is held at a trust dialog. `ask_which` writes a `which` row whose choices are the last `confirmation_needed`'s sessions the words matched (else the closest by status), at most 3. Routing is `talkRouter.ts`, the apps' rules; a shell is never a prompt's candidate. Rows `sent` and `started` are written by the daemon when the tool succeeded; `it` from the final text (none when empty); `failed` with `failureSentence`.
- **Conversations.** `talk.json` keeps `{agent, conversation: {date, agent, id}}`; a turn continues it only on the same day with the same agent, and a failed turn drops it. The agents' own files for it (Claude Code's under `projects/<work folder>`, Codex's rollouts) are theirs; `AllConversations` hides conversations whose folder is the work folder, so they are not listed to the apps.
- **The feed** (PROTOCOL.md "The feed", protocol 1.15.0; Adam): a `working`, `needsYou` or `finished` row for **every** session of an agent with `activity`, whether Talk sent to it or not, from its own status and words, at no model's cost (`talkFeed.ts` decides, `FeedWatcher` times).
  - `working`: the hook's prompt (`talk.noteAsked`, called beside `activity.noteAsked` in the Claude Code and Codex hook routes), one line. Not for a slash command or text that starts with `<` (Claude Code's own `<task-notification>`), and not for a turn Talk itself started (a prompt within 15 s of a `sent` or `started` to that session). Every hook prompt, written or not, marks the turn's start.
  - `needsYou`: the push rule (`startedWaiting`, `answer` or `stopped`) once the waiting held 1.5 s; `text` is `promptText` of the open card (it opens a moment after the status), else empty. Not again while it would repeat the session's last row.
  - `finished`: `done`, held 1.5 s, for a turn whose start this daemon saw (so a restart, which sees none, writes none for what it picks up); `text` is the turn's own reply from the activity store (`freshReply`: the newest `said` after the turn's `asked`), waited for up to 6 s because the transcript can lag the Stop (the `CatchUp`), else the session's summary, else empty.
  - One row per change: a waiting that flickers back within the settle writes nothing, and a row equal to the session's last row (feed, `sent` or `started`, also from the day's file after a restart) is not written again.
  - The Talk agent sees feed rows as data: in a new conversation's day summary only each session's newest feed row is kept (`daySummary`).
- **Tested end to end** against the running daemon (Claude Code 2.1.290, Opus 5.5): (the feed: a prompt typed into a test session gave `working` with it and `finished` with the start of its reply; a prompt Talk sent gave no `working` and `finished: PONG`) a send refused at a trust dialog, a send that arrived (the session answered PONG) with `sent`, `finished` and `it` rows, a `which` with two similarly named sessions and the tap's title sent on the next turn; Codex 0.160.0 ran and could not reach its tools; Codex 0.160.1 (`CODEX_BIN`, on a test daemon with its own `GRENADE_HOME`, ports 7799/7790 and `TMUX_TMPDIR`) sent, resumed its thread, and asked `which`.

## Highlights (`src/highlights/`)

Read PROTOCOL.md "Highlights" and SECURITY.md "Highlights" first. Once a session's turn has finished, the daemon finds what the turn made and writes the feed's `finished` row again with it; every client that watches gets the row as a `talk.entry` and replaces the one it has. No model is asked anything: everything comes from files the daemon already reads.

- **The turn** is from `turnStarted` (the hook's prompt, `UserPromptSubmit` for Claude Code and Codex's prompt hook, or the thread's own `sent` / `started` row) to the `finished` row's time, with 3 s of slack either side. The transcript's size at the start is remembered, so only the turn's lines are read for pictures. After a restart no start is known: the newest `asked` before the finish is the start, and the whole transcript is read once.
- **Boards**: the group's canvases (`listCanvases` of the folder its sessions share, as the canvas computes it), every board whose save time falls in the turn, with its address (`cwd`, `group`, `canvas`, `file`) so a client fetches it with `canvas.board` and renders it itself; the caption is its `<title>`, else its name. At most 18.
- **Screens**: `picturesIn` over the turn's transcript lines: a `Read` of a .png/.jpg/.jpeg/.webp/.gif, a `screencapture …` or `simctl io … screenshot …` command's output path, an `image` block of a tool result (what a browser tool showed the agent, inline). Each is kept once by `PictureStore` as a JPEG of at most 1280 px (the id is a hash of the bytes, so the same picture read twice is one tile); the caption is the agent's sentence nearest the picture's time within ten minutes, else the file's name. At most 12.
- **Yours**: the pictures in `attachments/<session>` saved in the turn, kept the same way; the caption is the first line of the prompt that named the file, else the first prompt after it. At most 6.
- **Shipped**: the turn's `push` activity entries that pushed something, as tiles with their `upstream` and `commits`.
- **Words**: `wordsOf` from the turn's activity: `asked` (the first prompt), `said` (the agent's first sentence when it is 20 characters or more and not a question), `chose` (prompts after the first board was saved), `said` (the last sentence). At most 12.
- **The look** runs 20 s after the `finished` row (`HIGHLIGHTS_DELAY_MS`: the transcript, the canvas and git have settled), once per session at a time; a turn that made nothing changes nothing. `gatherHighlights` orders tiles by time, `shipped` last, and keeps the newest 24.
- **Pictures are kept** under `<GRENADE_HOME>/highlights/` (folder 0700, files 0600) with a `.json` beside each (size, when kept, the session). Resized with `sips` on a Mac; on Linux with ImageMagick (`magick` or `convert`) when it is on PATH, else no picture is kept and rows have their boards and pushes only. Pruned after 30 days, at start and daily. `highlight.image` reads a copy by id; `highlight.remove` takes a tile out of the row (the row is written again) and deletes the copy; the agent's own file is never touched.
- **Tested**: `test/highlights.test.ts` (the transcript reading, the words, the gathering, the thread's `update`, the store with `sips` on a Mac); the connection's fixtures include `client.highlight.image.json` and `client.highlight.remove.json`.
