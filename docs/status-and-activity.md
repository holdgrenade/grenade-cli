# Status and activity

How status, models, prompts, summaries, activity, conversations and usage are worked out.

Part of `grenade-cli`: its rules and invariants are in the repo's `CLAUDE.md`.

## How status is derived (`src/sessions/status.ts`)

Pure reducer over events `{hook, output, asks, seen, gone}`; the registry feeds it timestamps. `asks` (a Codex dialog on the screen) is `waiting` / `answer` without `hookDriven`, and leaves an `idle` session that has seen it alone.

- New session starts `working`.
- Heuristic (any agent until a hook speaks): screen changed → `working`; no change for 1.5 s while `working` → `waiting`.
- Hooks (Claude Code, passed at launch as `--settings`, see "How a session works"): `UserPromptSubmit`/`PreToolUse`/`PostToolUse` → `working`, `Stop` → `waiting`, `StopFailure` → `waiting` (stopped), `SessionEnd` → `idle`. A `Notification` → `waiting` only when its `notification_type` says the agent is blocked (`permission_prompt`, `elicitation_dialog`, …; `waitingForClaudeHook` in the protocol); `idle_prompt` and the rest change nothing, because they arrive a minute after the agent stopped and used to raise a session the user had already seen. `PermissionRequest` → `waiting` too. Once a hook has been seen (`hookDriven`), screen changes no longer move status.
- Codex hooks (passed at launch as `-c` flags): `UserPromptSubmit`/`PreToolUse`/`PostToolUse` → `working`, `PermissionRequest` → `waiting` (answer), `Stop` → `waiting` (done), `Interrupt` (Esc) and `SessionEnd` → `idle` (`statusForCodexHook` in the protocol). Codex runs a hook only after the user trusted it ("Hooks need review" → "Trust all and continue", the first Codex Grenade starts), against a hash of each hook kept in `~/.codex/config.toml` under `/<session-flags>/config.toml:<event>:0:0`: the flags are the same for every session (the id is `$GRENADE_SESSION` at run time), and every change to `codexHookCommand` or the event order asks for the trust again. Until trusted, a Codex session is heuristic like before.
- Why it waits: the reducer keeps `waitingFor` (`answer` for a question or permission prompt, `done` for a finished turn or a stable screen) and the Session shows it only while `waiting` (`shownWaitingFor`). A new reason on a waiting session counts from now and emits `updated`. The reason survives `idle` as "what the user has seen": a hook that repeats it (the `Notification` that follows a `PermissionRequest`) leaves the session `idle`. `working` forgets it.
- Background tasks (PROTOCOL.md "Background tasks"): a turn that ends with work still running is not finished. A Claude Code `Stop` whose `background_tasks` lists a task (`claudeBackgroundTasksIn`) calls `registry.holdForBackground`: the reducer keeps the session `working` with `background: true`, the registry puts the tasks on the Session (`background`, without the agent's ids) and saves them in `sessions.json`, so a restarted daemon holds it again (`restoreHeld`). The hold ends with a hook of the agent's own turn (the `UserPromptSubmit` Claude Code sends itself when a task ends, then a `Stop` with what still runs), or with `registry.backgroundOver` (→ `waiting`, `done`): `ClaudeBackgroundWatch` calls it when a task was stopped in Claude Code's task view, which fires no hook. A held session is never taken for a turn that stopped partway (it shows no spinner by design), is not `isBusy` (a server left running would keep the daemon from ever restarting into an update), gets its summary at the hold, and an Esc from a phone does not mark it stopped. Codex's hooks say nothing about its background terminals: `codexBackgroundIn` reads "N background terminal(s) running" off the screen, at its `Stop` hook (`background` in `CodexHookListeners`) and on every changed capture (`watchScreenBackground` → `registry.screenBackground`), which also holds a session that finished a moment before its screen showed the line (the 3 s push grace covers that second of `done`), and ends the hold when the line is gone. Tested end to end against a test daemon (ports 17788/17789, own `GRENADE_HOME`, `TMUX_BIN` wrapper on a private socket, Codex with its own `CODEX_HOME`): Claude Code 2.1.288 held on `sleep 25` and finished when it ended, held on `sleep 300` and finished 3 s after the task was stopped by hand; Codex 0.160 held on `sleep 40` and finished when its line went.
- Hooks from inside a subagent: a Claude Code tool hook that carries `agent_id` is an aside (`applyHook` with `aside`), as is a prompt answered from a phone. Claude Code runs side agents of its own after a turn (prompt suggestions), and their `PreToolUse` used to turn a finished session `working` with no `Stop` to follow, so 30 s later it read as stopped partway. An aside changes nothing on a session whose turn is over, never ends a background hold, and turns a session that waits for an answer `working` again (held again, if it was held before the question).
- `seen` (client is looking): `waiting` → `idle`. `waiting` for 10 min → `idle`. Neither applies to a turn that stopped partway.
- A turn that stopped partway (PROTOCOL.md "A turn that stopped partway"): `StopFailure` → `waiting`, `waitingFor: "stopped"`, `stoppedBecause: "error"`. A hook-driven `working` Claude Code session whose screen shows no spinner (`claudeIsWorking`, passed in the `output` event as `busy`) and has not changed for 30 s (`STOPPED_QUIET_MS`) stops too: `sleep` when a look during the turn came 30 s or more after the one before (`SLEEP_GAP_MS`: the poller looks every second, so the Mac slept), else `quiet`. Only a working, hook-driven turn keeps `lastLookAt`, so other states return the same object. A new turn forgets `sleptThisTurn` and the reason. The Session shows `stoppedBecause` only while stopped (`shownStoppedBecause`). `wsHandler` sends each client `sessionFor` its version, so an app from before `stopped` sees `done`. Push sends it as an `answer` event with a line saying why (`STOPPED_PUSH_TEXT`). Installs from before 1.0.20 lack the `StopFailure` hook until `grenade install-hooks` (or `setup`) runs again; the quiet rule covers them.
- tmux session missing on the 1 s sweep → `gone`, terminal. The cached screen stays servable.

Model: every applied hook with a `transcript_path` makes the daemon read the tail of that transcript and set the session's `model` to the label of the last assistant reply (`<synthetic>` replies are skipped). It changes after a `/model` switch once the next reply lands, is saved in `sessions.json`, and is absent for shell sessions. A Codex session's `model` is the `model` slug of its last hook (`gpt-6-luna`), as Codex names it. A failed read is logged at debug and leaves the old model.

Effort: the same read takes the reply's `effort` (Claude Code writes it on every assistant line) and its `timestamp`, and `registry.setModel(id, model, effort, at)` puts both on the session. Codex's hooks name no level, so a Codex session carries none.

Folder: a session's `cwd` follows the agent. Neither the hook payload's `cwd` nor tmux's `pane_current_path` moves when Claude Code's shell runs `cd` (both stay at the process's folder), but Claude Code stamps every line it writes to the transcript with its shell's `cwd`, so the same transcript read that feeds the activity applies `workingDirectoryIn` (protocol) and calls `registry.setCwd`, which persists it and emits `updated`. A `cd` by the Bash tool shows with the next hook; a `cd` typed as a `!` command shows at the `Stop` of that turn (the `environment` line Claude Code writes for a change comes only with the next prompt, which is why the stamp is read, not that line). Codex and shell sessions keep the folder they started in.

Only sessions launched by Grenade have `GRENADE_SESSION` in their environment; hook posts without `?session=` are answered 202 and ignored.

## Models (`src/models/`)

Read PROTOCOL.md "Models" first. An app switches a running session to another model with `session.model`, **for that session only**: the model and effort saved in the agent's own settings are never changed (Adam chose option A of the "Grenade Model Picker and Handoff" canvas).

- What can be chosen is `models` on the agent in `agentCatalog.ts`: for Claude Code the four current models, named as its picker's rows and as `modelLabel` names them, each with its effort levels (Haiku takes none). Codex and the shell list none, so the apps only show their model. Codex is left out because its `/model` saves the choice as the default and it could not be run in a test terminal to read its picker.
- `Connection` refuses what is not a choice (`modelChoiceProblem`) and a session whose agent is not at its prompt (`switchTimingProblem`: `working`, waiting for an `answer`, `gone`) with `bad_frame`. A choice the session already has is answered with `session.updated` to the sender and touches nothing.
- Claude Code has no command that switches one session only: typing `/model <name>` saves it as the user's default, and so does Enter in the picker. The picker's `s` key does not. So `switchClaudeModel` types `/model`, checks that the prompt box holds exactly that (text someone left there would be sent as a prompt: it takes its six characters back out and refuses), presses Enter, reads the picker (`modelPickerIn`), moves the cursor one row at a time until it is on the model, presses Right until the effort line says the level (the levels go round), and presses `s`. It never presses Enter in the picker. A picker without "s to use this session only" (an older Claude Code) is closed with Esc and refused.
- It reads the screen after every key, so a list in another order, or scrolled, is still steered right; a model the picker does not have ends in Esc and `ModelSwitchError` after 20 moves. Success is the picker closing and a "Set model to <name> for this session only" line; anything else on the screen (Claude Code asking about usage credits for a model) is left for the terminal and reported.
- **Claude Code asks "Switch model?" first** whenever the conversation has a message (its history is cached for the model it had; 2.1.289). For a switch from an app `switchClaudeModel` presses its "Yes" (the selected row's keys from `claudeDialogIn`) and waits for "Set model to …" as for a switch that was not asked about: choosing in the app was the answer (Adam: CLI 1.0.44 to 1.0.46 sent it as a card and an error, and on the iPhone the card opened under the model sheet, which stayed up). While a switch runs, `ScreenPrompts` ignores that session's screens (its `steering` check is `switchingModel`), so the question never flashes up as a card. A question still up after Yes ends in `ModelSwitchError`, and the card opens on the next capture. The card is PROTOCOL.md "Claude Code dialogs" (`claudeDialogs.ts`) and is now for a `/model` typed in the terminal: "Switch" presses Yes, and when the dialog is gone and the screen says "Set model to <that model> for this session only with <level> effort", `ScreenPrompts` calls `registry.chooseModel` with both. "Don't switch" (and a dismissed card) presses "No, go back", which leads back to the picker, and then Esc once the picker is on the screen. A switch of the effort level alone is not asked about.
- While that dialog is up the session is `waiting` for an `answer` (`registry.asks`). No hook says it is over, so a hook-driven session remembers what it was (`beforeAsk` in `status.ts`) and `registry.asked` puts it back when the screen moves on: `idle`, `waiting` for `done`, or a turn that stopped partway with its reason; a finished turn that was looked at meanwhile is `idle`; a hook in between wins. A session whose status comes from the screen (Codex before its hooks are trusted) is left to the screen, as before.
- It talks to tmux directly (`ModelTerminal` in `server.ts`), not through `registry.sendText`: what it types is no prompt. One switch per session at a time.
- On success `registry.chooseModel` sets `model` and `effort` at once and remembers when (`modelChosenAt`, saved in `sessions.json`): the next hook reads the transcript's last reply, which is from before the switch, and `setModel` ignores a reply written before the choice. The first reply after it takes over again.
- A model picked without an effort keeps the level the picker shows, which is the session's current one, not the model's default.
- A `tmux_failed` error carries the `ModelSwitchError`'s sentence, written for the person who chose.
- Tested against Claude Code 2.1.289 in a tmux server of its own: seven switches across four models and four levels took under a second each, `model` and `effortLevel` in `~/.claude/settings.json` stayed as they were, text left in the prompt box was refused and left intact, and a model the picker lacks ended with the picker closed. `test/claudeModelPicker.test.ts` holds that picker's screen. "Switch model?" was tested end to end (Claude Code 2.1.289, a test daemon on ports 17788/17789 with its own `GRENADE_HOME` and a `TMUX_BIN` wrapper on a private socket, a scripted client): after one message, `session.model` got the `prompt` and then the error within 0.6 s, "Don't switch" left "Kept model as …" and the prompt box with the session `waiting` for `done` again, "Switch" set `model` and `effort` 0.2 s later, and an effort-only switch went through unasked. `test/claudeDialogs.test.ts` holds the dialog's screen. The app switch that presses Yes itself (1.0.47) presses the same keys as that "Switch" and is covered by `test/claudeModelSwitch.test.ts`, not yet by a run against Claude Code.

## Prompts (`src/prompts/`, `src/daemon/promptHook.ts`)

Read PROTOCOL.md "Prompt hook" and "Prompts" first. A phone can answer a permission request, a question (`AskUserQuestion`) and a plan (`ExitPlanMode`) with one tap.

- Claude Code runs its `PermissionRequest` hook the moment it shows one of those, and shows it in the terminal at the same time. Ours is an HTTP hook to `POST /hooks/claude/prompt` that stays open for up to 12 hours (`PROMPT_HOOK_TIMEOUT_S`). The first answer wins, terminal or hook.
- The route applies the event through `handleClaudeHook` like any hook (so status, `waitingFor` and push need nothing special), opens the prompt in the `PromptStore`, and keeps the response. The store emits `opened`; every `Connection` forwards it as a `prompt` frame, and a phone that says `hello` later gets the open ones after `sessions`.
- `prompt.answer` → `PromptStore.answer` → `hookReplyFor` (protocol) builds the reply, the held response is sent, `closed` with `answered` goes to every phone, and the session is set `working`.
- Answered in the terminal: a "no" or an interrupt makes Claude Code drop the request at once (`res.on("close")` → `dropped`); a "yes" leaves the request open, and the `PostToolUse` that follows closes the prompt (`closePromptsByHook`), which answers the request with an empty 200. `Stop`, `UserPromptSubmit` and `SessionEnd` close everything the session had open.
- Every answer of the route is a 200. An empty one leaves the prompt to the terminal; anything else would show up in Claude Code as a hook error. That is also what a session the daemon does not know gets, and a Claude Code that Grenade did not start.
- A question and a plan only accept an `allow` that hands `tool_input` back as `updatedInput`; a bare `allow` leaves the dialog open. `fixtures/prompt.examples.json` pins every reply, and `test/promptStore.test.ts` replays it.
- Replies never carry `updatedPermissions`: an answer from the phone counts once.
- Open prompts are in memory only. `stop()` calls `closeAll()` first, because a held request would keep the HTTP server from closing.
- `grenade prompt test` puts a test card on a session (the named one, else the first that is running) through `POST /prompts/test` on the control API and waits on `GET /prompts/test/:id`. It goes through the same store, frames and reply builder as a real prompt; only the held hook request is missing, so no agent is asked and nothing runs. It does not change the session's status and sends no push, and the hooks of the session's agent do not close it (`test` in the store), so it can sit on a session that is busy.
- Codex's startup dialogs (PROTOCOL.md "Codex dialogs"): `registry.updateScreen` emits `captured` for every changed capture; `ScreenPrompts` runs `codexDialogIn` on Codex sessions (and `claudeDialogIn` on Claude Code's, see "Models"), opens one card per dialog through `openScreen` (status `asks`, so a session whose hooks never get trusted stays heuristic), answers with `registry.sendKey` per key, and closes the card with `elsewhere` once the screen no longer shows that dialog. An answered card's dialog stays known until the screen moves on, so the same dialog opens no second card while its keys are on their way, or after a dismissal that left it to the terminal. A screen card sends no `answered` (the screen says what happens next) and no hook closes it. Tested end to end: Codex 0.160 started by a test daemon (own `GRENADE_HOME`, `CODEX_HOME`, ports 17788/17789, `TMUX_BIN` wrapper on a private `-S` socket), a scripted phone answered Trust, Codex saved all seven hooks as trusted and they reported.
- To try it without touching the running daemon or `~/.claude/settings.json`: write `mergeHooks({}, 7799).settings` to a file, put a `claude` wrapper that adds `--settings <file>` first on `PATH`, point `TMUX_BIN` at a wrapper that runs `tmux -L <name>`, and start a daemon with its own `GRENADE_HOME` on other ports.

## Summaries (`src/summary/`)

Each session carries `summary`, one sentence on what it is working on, and `title`, a few words naming it, shown as the row's heading on the phone and the Mac with the session's `name` beneath. The daemon writes both with Haiku through the `claude` CLI (one reply: the title on line 1, the summary on line 2), so it uses the Mac's Claude Code login and needs no API key.

- `title` for a Claude session is Claude Code's own title, the same one a past conversation shows: every transcript read (`readActivity` in `server.ts`) looks for the newest `ai-title` line (`aiTitleIn`) and calls `registry.setAiTitle`. The summarizer's title (`setGuessedTitle`) shows only until Claude Code has written one, and for Codex and shell sessions. Both are saved in `sessions.json`.

- Triggers: status becomes `working` (run 8 s later, so the screen shows the task), status becomes `waiting` (run now), and a `UserPromptSubmit` prompt (kept, last three per session). A pending run absorbs later triggers.
- Limits: one run per session per minute (`summaryDelay`), one run at a time overall, and no run when the model input (prompts + last 60 screen lines) hashes the same as last time. A failed run clears the hash so the next trigger retries; only the first failure in a row is a warning.
- The call is `claude -p --model haiku --tools "" --setting-sources "" --strict-mcp-config --no-session-persistence --system-prompt …`, run in the temp folder with `GRENADE_SESSION` removed. No settings means no hooks, so a summary never reports status for itself. Do not use `--bare`: it skips the keychain, so a subscription login stops working.
- A run takes about 2–6 s, and the first run after boot can take 30 s. The timeout is 60 s.
- `summary` and both titles are saved in `sessions.json` and restored on `adopt()`. Off: `--no-summaries`, `GRENADE_SUMMARIES=off`, or no `claude` found (logged once at start).

## Activity (`src/activity/`)

Read PROTOCOL.md "Activity" first. The phone's plain view of a session is what the agent said and was asked, in the words of its transcript, with no tool calls and no output.

- Codex: the `transcript_path` of a Codex hook is its rollout (`~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`), read by the same `TranscriptReader` and picked by `codexActivityEntriesIn` (protocol, pinned by `fixtures/codex.rollout.examples.jsonl`); `readActivity` in `server.ts` chooses the rule by the session's agent, and reads no folder or title from a rollout. A Stop with no `said` gets the same `CatchUp`. An `Interrupt` hook whose read has no `stopped` starts `codexStopCatchUp`, which reads until Codex's `turn_aborted` line is there. The daemon says `codexActivity: 1` (retired, for apps from before) and `activity: true` on Codex in `daemon.agents`, and apps show a Codex session's plain view only then. Tested end to end: Codex 0.160 in its own tmux socket and `CODEX_HOME`, the real hook command, a test daemon (own `GRENADE_HOME`, ports 17788/17789, fake tmux).
- Source: the `transcript_path` every Claude Code hook carries. On each hook the `TranscriptReader` reads the file from where it left off (whole lines only, so a line still being written waits for the next hook) and `activityEntriesIn` from the protocol picks the lines that count; the same read gives `workingDirectoryIn` the session's current folder. The same rule pins `fixtures/transcript.examples.jsonl` to `fixtures/daemon.activity.json`, so what counts is decided in the protocol, not here.
- A `Stop` hook can run before Claude Code has written the reply to the transcript (seen in one run of three with `claude -p`), and in a turn without tool calls no later hook reads it, so the reply used to reach the phone only with the next prompt. When a Stop's read brings no `said` entry, `CatchUp` reads the transcript again after 250 ms, 500 ms, 1 s, 2 s, 3 s and 5 s until one arrives; any hook of the session, or its removal, cancels it.
- `ActivityStore` keeps the last 200 entries per session in memory only. The transcript path of each session's last hook is saved in `sessions.json` (`registry.setTranscript`, never sent to a phone), and a starting daemon reads every saved transcript from its beginning (`registry.transcripts()`), so the history is back before a phone subscribes instead of after the session's next hook. Daemon updates restart it often, and an idle session used to show the empty "Waiting for your first prompt" card until it was prompted again. A session that has had no hook since 0.1.12 has no saved path and waits for its next hook. A removed session is forgotten.
- A `UserPromptSubmit` hook's `prompt` goes into the store at once (`noteAsked`), because Claude Code writes the prompt to the transcript after the hook. When the transcript's copy arrives, the hook's entry gives way to it, so the entry sits where the transcript has it. The prompt is read with the protocol's `typedPromptText`, the transcript's own rule, so both have the same text: a prompt with a line break (typed in as a paste, which every Canvas chip prompt is) comes wrapped in `<pasted_content …>`, and until 1.0.57 that `<` made the daemon skip it, so it showed only at the next hook's read, or never when it was sent mid-turn. Slash commands and text that still starts with `<` are not the user talking and are skipped. A prompt sent while the agent works fires its hook at once, but Claude Code takes it into the turn later and writes it only as a `queued_command` attachment, which the protocol counts as `asked`; several can wait for their copies at once (`pending`, at most `PENDING_KEEP`), each copy matched to the oldest waiting entry with its text.
- `Connection` sends the store's entries with `full: true` when a phone subscribes to a Claude session, and forwards each new batch while it stays subscribed. Shell sessions have no transcript and get no `activity` frame. `stopped` entries are left out for an app from before them (`activityFor` from the protocol, by the `hello`'s `client`), and a batch left empty is not sent.
- Stop: an interrupt (Esc in Claude Code) fires no hook, but Claude Code writes "[Request interrupted by user…]" to the transcript, which the protocol reads as a `stopped` entry. After a `key` frame of `escape` or `ctrl-c` the `Connection` calls `interrupted`, and for a working Claude session `server.ts` runs a second `CatchUp` that reads until a `stopped` entry turns up. Any read whose newest entry is `stopped` turns a working session `idle` (`endsStopped`). A prompt stopped before Claude wrote anything leaves no line at all, so when a catch-up read finds none but the screen no longer shows Claude Code working (`claudeIsWorking` in `src/activity/claudeScreen.ts`, pure, tested: the spinner line "✻ Elucidating… (12s · …)" or "esc to interrupt"), the session turns `idle` and `ActivityStore.noteStopped` adds the entry (the transcript's late copy is dropped). Esc typed in the terminal itself is seen at the next hook.

## Changes (`src/changes/`)

PROTOCOL.md "Changes". `ChangesTracker` keeps each session's `Session.changes` (`registry.setChanges`, which sends `session.updated` only when it differs): it reads the session's folder when the session is created, 0.5 s after a hook of its agent (Claude Code's and Codex's routes call `noteHook`; a burst of hooks is one read), after a push, and every 10 s for every live session, so a commit made in a terminal shows too. One read at a time per session; a request during one reruns it once it ends. A read is `git status --porcelain=v2 --branch -z --untracked-files=all`, `git remote`, `git diff <HEAD> --numstat -z -M`, the first MB of each untracked file (to count its lines; a NUL byte makes it binary), and two `git log` / `rev-list` for the commits waiting. The daemon never fetches.

The session's commits are those after `gitBase`, the commit checked out at its first read, saved in `sessions.json` (`setGitBase`), so a restart still counts them. Without an upstream the waiting commits are those; with one, those the upstream lacks.

**The push card.** The tracker remembers which commits were waiting at the last read. When a read finds some gone and the upstream has them (`git merge-base --is-ancestor`), they were pushed: one `push` entry (`ActivityStore.notePush`) with up to 20 of them, short hashes. So a push by the agent, by `git.push` or by the user in a terminal reads the same; a rebase or an amend (commits gone, but not upstream) adds nothing, and the first read after a restart adds nothing.

**`git.push`** reads the folder, refuses with `bad_frame` when `canPush` says no, sets `pushing` (a `session.updated`), runs `git push` (or `git push -u <remote> <branch>`; 60 s; `GIT_TERMINAL_PROMPT=0`, so a push that needs a password fails as `auth` instead of hanging), clears `pushing` and reads again, which adds the card. A failed push adds its own entry (`failed`: `behind`, `auth` or `other` with git's first line). It runs with the computer's own git setup: credentials, hooks, signing.

`changes` and `changes.diff` run git in the repository's top folder (a path is relative to it). A diff of a tracked file is `git diff <HEAD> -M -- <path>`; an untracked one `git diff --no-index -- /dev/null <path>`; a commit's `git show --format= -M <hash> -- <path>`.

## Conversations (`src/conversations/`)

Read PROTOCOL.md "Conversations" first. A phone lists the conversations every agent saved on the Mac (Claude Code's and Codex's), previews one, resumes it as a copy, or deletes it. **Grenade never writes an agent's file, and removes one only on `conversation.delete`, into the macOS Trash**: the agents' own `/resume`, `codex resume` and their apps use the same files. Each agent is a `ConversationSource` and `AllConversations` merges them; nothing outside a source knows an agent's files (PROTOCOL.md "Agents": no frame names an agent). A client that sends `conversations` without `anyAgent` (apps from before) gets Claude Code's only, and the connection keeps to that for the lists it sends after a delete.

- Where: `paths.claudeDir` (`CLAUDE_CONFIG_DIR`, else `~/.claude`). `projects/<folder>/<id>.jsonl` are the conversations (subagent transcripts sit deeper and are skipped); `sessions/<pid>.json` are Claude Code's running processes, which say `running`. Both are Claude Code's own undocumented files: anything unexpected counts as nothing, never as an error.
- A row is read from the first and last 128 KB of a transcript and cached by mtime and size: about 0.5 s for 350 conversations the first time, a few ms after. A transcript without a typed prompt, or whose folder is gone, is not listed.
- Resume: `session.create` with `resume` goes to `ConversationsPort.resume` in server.ts, which finds the transcript and starts `claude --resume <id> --fork-session` in the conversation's own folder (`agentCommand`, which checks the id again because tmux hands it to a shell). The session carries `resumedFrom`/`resumedAt` (saved in sessions.json). Its activity is the original's history at once (read whole, not through the TranscriptReader, whose place in that file may belong to another session).
- Claude Code writes the copy only with its first prompt, so until then the session's saved transcript is the original. The first hook names the copy: `marks.noteCopy` records it, and since the copy's first read starts at its beginning (`readChunk` `fromStart`) and repeats the history, `activity.replace` takes it in place of what the store held and sends one `full` frame. A hook prompt the copy does not hold yet stays last. Sessions that were not resumed always `append`, as before.
- Delete (Adam: "Archive" in the apps deletes): `conversation.delete` → `ConversationsPort.delete` in server.ts → `ConversationIndex.trashPaths` (the transcript and the folder of the same name beside it; refused while a live Grenade session holds it or another Claude Code process has it open, because either would write it again) → `moveToTrash` (`src/conversations/trash.ts`, `/usr/bin/trash`, macOS 15+), so it can be put back from Finder. A refusal is `bad_frame` with the reason. The 1.0.14 `conversation.archive` is answered with the list and changes nothing, and the archived ids 1.0.14 saved are dropped.
- Tested end to end against a test daemon (own `GRENADE_HOME`, ports and `TMUX_TMPDIR`): list, preview, resume, history before the first prompt, the switch to the copy, the original's size unchanged, the copy listed with `copyOf`, archive. ## Usage (`src/usage/`)

Read PROTOCOL.md "Usage" first. A session carries `context` (tokens in its context out of the model's window), and a client asks `limits` for each agent's plan windows on this computer (`limits: 1` in the `daemon` object, protocol 1.12.0). The apps show "38% · Opus 5.5 ⌄" in a session's header and the rest when that number is tapped (the "Grenade Token Usage" canvas).

- **Claude Code says both only to its status line.** Its hooks carry no usage; the JSON it pipes to a `statusLine` command after each update has `context_window` (`current_usage`, `context_window_size`, `used_percentage`) and, on a Pro or Max plan, `rate_limits.five_hour` / `seven_day` (`used_percentage`, `resets_at` in Unix seconds). So `claudeHookFlags` puts a `statusLine` in the `--settings` it starts Claude Code with: `in=$(cat)`, the payload posted to `POST /hooks/claude/status?session=$GRENADE_SESSION` in a background subshell (loopback only), then the user's own line run with `sh -c` on the same payload, its output being the line. The user's line is read from `settings.json` as each session starts (a getter on `AgentFlags.claude`), so a change applies to sessions started after it; `padding` is kept. Without one the line is empty, as before. A `--settings` status line wins over the user's, which is why Grenade's runs theirs. `install-hooks` writes no status line, so a `claude` typed by hand reports no usage.
- **No guess from the transcript.** The window depends on the model and the plan (Opus 5.5 on Max had 1 000 000), which the transcript does not say, so a Claude session has no `context` until its status line has reported. Sessions started before 1.0.50 never do.
- **Codex** writes a `token_count` event to its rollout after each turn with `last_token_usage`, `model_context_window` and `rate_limits` (`primary`, `secondary`: `used_percent`, `window_minutes`, `resets_at`). Every Codex hook with a `transcript_path` reads the rollout's tail (`readCodexUsage`), sets the session's `context` and records the limits.
- `registry.setContext` emits `updated` when the numbers change; `context` is not saved in `sessions.json`. `PlanLimits` is in memory: after a restart an agent has none until it reports again.
- Tested end to end: a test daemon (ports 7799/7790, own `GRENADE_HOME` and `TMUX_TMPDIR`) started Claude Code 2.1.289, one prompt later the session had `context` 93 416 of 1 000 000 and a scripted phone's `limits` got the five-hour and weekly windows. Codex was not run live; `test/usage.test.ts` holds a real `token_count` line and a real status line payload.
